# Единые правила работы Codex

Это главная обязательная инструкция для всех людей и Codex в репозитории HackAlem AI.

## 1. Приоритет инструкций

При противоречии применять правила в таком порядке:

1. Официальные правила и задание HackAlem.
2. Явная текущая команда пользователя.
3. Этот корневой `AGENTS.md`.
4. Локальный `AGENTS.md` рабочей области.
5. GitHub Issue или задача в `docs/TASKS.md`.

Локальный `AGENTS.md` только дополняет корневой. При неустранимом противоречии Codex останавливается и сообщает о нём.

## 2. Источники правды

- GitHub: код, ветки, commits, PR, Issues и история.
- `docs/CASE.md`: официальный кейс, MUST-требования и критерии приёмки.
- `docs/TASKS.md`/Issue: владелец, статус, область, критерии и ветка задачи.
- `docs/API_CONTRACT.md`: общие интерфейсы и форматы данных.
- `docs/DECISIONS.md`: межзонные и архитектурные решения.
- `docs/HANDOFF.md`: краткое текущее состояние и следующий шаг.
- `docs/WORKLOG.md`: подробная история работ и проверок.

Если Issue и `docs/TASKS.md` расходятся, не начинать работу до синхронизации владельца и статуса.

## 4. Обязательный цикл задачи

### До начала

1. Проверить `git status --short --branch`, текущую ветку, remote и незавершённые изменения.
2. Выполнить fetch/pull, если это не затрёт незавершённую работу.
3. Прочитать: корневой и локальный `AGENTS.md`, `CASE`, `TEAM`, свою задачу, `DECISIONS`, `HANDOFF`, `API_CONTRACT`, `ARCHITECTURE` и связанные записи `WORKLOG`.
4. Убедиться, что задача не занята другим участником.
5. Указать в задаче владельца, область, ветку и статус `In Progress`.
6. Создать короткую ветку своего префикса. Не работать прямо в `main`, кроме явно согласованных репозиторных правок.

### Во время работы

- Делать минимальные целевые изменения и сохранять совместимость.
- До изменения общего контракта обновить `API_CONTRACT` и `DECISIONS`, затем сообщить зависимым участникам.
- Не коммитить secrets, API keys, tokens, credentials и реальные `.env`.
- Не додумывать отсутствующие требования.
- Собрать минимальный сквозной путь: `input -> backend/core -> result -> frontend`.
- Сообщать о блокерах и зависимостях.

### Перед завершением

1. Просмотреть полный `git diff` и убрать случайные свои изменения.
2. Запустить все доступные tests, lint, typecheck, build и smoke/integration checks.
3. Указать точные команды и результаты. Не заявлять об успехе незапущенных проверок.
4. Обновить Issue/задачу, `WORKLOG` и компактный `HANDOFF`.
5. Указать файлы, результат, ветку, commit SHA, PR, блокеры и следующий шаг.
6. Перевести задачу в `Review` или `Done` только по её критериям готовности.

## 5. Git-процесс и разрешения

- Обычный процесс: `main -> short branch -> commit -> push -> PR -> CI/review -> merge`.
- Codex разрешено самостоятельно выполнять `git add`, `git commit` и обычный `git push` после доступных проверок.
- `force-push`, merge, удаление веток и перезапись истории запрещены без отдельного явного разрешения.
- Не пушить поверх новых remote-изменений: сначала fetch, сравнение и безопасная синхронизация.
- Красный CI означает, что задача не готова к merge.

## 6. Общие контракты

- Разделять domain adapter, optimization/core, evaluator, API, frontend и tests/integration.
- До параллельной работы зафиксировать endpoint/function, request, response, types, errors и environment variables.
- Frontend может использовать mock, точно совпадающий с `docs/API_CONTRACT.md`.
- Traffic optimization — только sandbox; официальный кейс имеет приоритет.

## 7. Definition of Done

Задача готова, только если:

1. Критерии готовности выполнены.
2. Проверки прошли или их ошибки/невозможность точно записаны.
3. Контракты совместимы или их изменения согласованы.
4. Нет секретов, случайных файлов и затёртых чужих изменений.
5. Задача, `WORKLOG` и `HANDOFF` обновлены.
6. Ветка и commit отправлены; PR создан, если он используется.

## 8. До выдачи официального кейса

Готовить доступы, инструменты, docs, шаблоны и dry run. Не считать заранее написанный solution-code разрешённым без подтверждения организаторов.
